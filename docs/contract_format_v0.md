# monban 契約ファイル形式 v0(凍結)

日付: 2026-07-31
起草: 番頭(agent:claude)。凍結すべき API 三つ(契約ファイル形式・台帳イベントスキーマ・
MCP ツール名)の第一号。台帳イベントスキーマは banto 契約 v1 を輸入するので、
monban が自前で凍結する最初の形式がこれになる。
状態: **v0 凍結**(2026-07-31、主人の委任による)。改訂は編集ではなく版上げ(`monban/1`)。

## 設計の根

- **プロンプトは願い、これは契約。** エージェントに「こうしてほしい」と頼む文ではなく、
  「この証拠がなければ通らない」を機械が執行できる形で書く
- **契約は門より先に在る。** 門は契約を読むだけで、その場で要件を発明しない。
  改め(verify)の時点で契約ファイルのハッシュを台帳イベントに結び、
  「どの契約で通したか」が後から検査できる
- **書くときは人間、読むときは機械。** 一人親方が手で書ける短さを保つ。
  banto.toml と同じ TOML

## ファイル

作業ディレクトリ直下の `monban.toml`。banto.toml と並んで置かれる想定。

```toml
schema = "monban/0"

# ── 関(せき)= 通過点の定義。claim はいずれかの関を名指しで通る ──

[[seki]]
name = "tests-pass"
title = "テストが通っている"

  # 証拠タイプ第1号: 門番が自分で走らせるツールチェーン
  [[seki.evidence]]
  kind = "toolchain"
  cmd = ["cargo", "test", "--workspace"]
  expect_exit = 0

[[seki]]
name = "report-honest"
title = "レポートの数字は実行過程に裏付けがある"

  # 証拠タイプ第2号: 独立コレクタの蔵にある OTel span
  [[seki.evidence]]
  kind = "otel"
  vault = "/var/otel-vault/vault_export.jsonl"
  span = "count_lines"                    # 必須 span 名
  attrs_match = ["lines.total"]           # 成果物と突き合わせる属性
```

## 語彙

| 語 | 意味 |
|---|---|
| 関 seki | 契約上の通過点。claim は関を名指しで declare する |
| evidence | 関を通るのに必要な証拠の要件。複数あれば**全部**(AND)。OR は関を分けて表す |

## 各欄の規則

### `schema`(必須)

常に `"monban/0"`。改訂は編集ではなく版上げ(`monban/1`)。banto 契約 v1 と同じ思想。

### `[[seki]]`(1個以上)

- `name`: 小文字ケバブケース。台帳の claim イベントがこの名前を参照する
- `title`: 人間向けの一文

### `[[seki.evidence]]` — `kind = "toolchain"`

- `cmd`: **固定 argv 配列**。シェル文字列は受けない(注入と「説得」の余地を残さない)
- `expect_exit`: 期待する終了コード(既定 0)
- 実行するのは**門番自身**。エージェントが持ち込んだ実行結果は、この kind の証拠にならない。
  終了コードと出力ハッシュが台帳に残る

### `[[seki.evidence]]` — `kind = "otel"`

- `vault`: 独立コレクタの蔵(門番が読む。エージェントは書けても読めない)
- `span`: 蔵に存在すべき span 名
- `attrs_match`: 成果物側の値と突き合わせる span 属性名の列

## 執行の規則(形式の外だが、形式が前提にするもの)

1. 関に `evidence` が一つもない契約は**ロード時に拒否**する(証拠なしの関は門ではない)
2. declare 時、門番は契約ファイルの sha256 を claim イベントの evidence に結ぶ。
   契約の差し替えは改めの前提を変えるので、必ず台帳に写る
3. 改めの判定(pass/fail)は banto の `claim.verify` として台帳に追記される。
   verify の actor は門番(`agent:monban`)であり、declare した actor と必ず別になる
4. 人間の上書き裁可は、契約の外の権限として常に残る(門は主人を締め出さない)

## v0 で決めないこと

- 証拠タイプの追加(HTTP 応答、ファイル存在検査など)は v1 以降。二つで一点突破する
- 関の依存関係(A が通らないと B に入れない等)は入れない。平らな関の列だけ
- タイムアウト・リトライなどの実行詳細は実装の裁量とし、形式には載せない

## v0 凍結時の決定(2026-07-31)

1. **語は「関」で確定。** 江戸の層(門番・手形・改め)に沿わせる。
2. **置き場は `monban.toml` で確定。** banto.toml と並ぶ。
3. **`kind = "otel"` は v0 では「予約」。** 形式には載るが、v0.1 の執行機は
   ロード時に「未実装」として契約ごと拒む(執行できない約束を受け取らない)。
   `attrs_match` の突き合わせ先の書き方は otel 実装時に固める。

## 凍結 API 第三号: MCP ツール名(先行凍結)

エージェント向けの唯一の入口となる MCP ツール名は **`monban.declare`** とする。
実装は v0.2(名前だけを先に凍結し、実装がこれに従う)。
引数は契約形式と台帳スキーマから導出される: `seki`(関の名前)・`title`(主張の一文)・
`evidence`(成果物パスの列)。改めに相当する MCP ツールは**存在させない** —
改めは門番自身の仕事であり、エージェントに口を与えない(三条二)。
