# OTel 証拠(kind = "otel")の検分規則 v0(2026-07-31)

契約形式 v0 の凍結時決定3「`attrs_match` の突き合わせ先の書き方は otel 実装時に固める」を、
ここで固める。実装は monban v0.3。契約の欄の定義は
[docs/contract_format_v0.md](contract_format_v0.md) が権威、検分の規則は本書が権威。

## 蔵の形式 — 発明しない

蔵(`vault`)は、独立コレクタの受領記録。**OTel Collector の file exporter が吐く
OTLP/JSON 行**(1行 = `ExportTraceServiceRequest`)をそのまま読む。
monban のための特別な形式は無い — 既にあるエコシステムの出力が、そのまま証拠になる。

## 検分の規則

改め(verify)の時点で、門番は次を順に確かめる。**どれか一つでも欠ければ通らない**:

1. 蔵が読める。全行が OTLP/JSON として解析できる(壊れた蔵は証拠にならない)
2. 契約が名指しする `span` が、蔵に**1本以上**在る(過程の証言が無い主張は通らない)
3. **同名のすべての span** について、`attrs_match` の各属性が:
   - 存在する
   - スカラー(string / int / double / bool)である。正規化は
     string そのまま・int と double は十進表記・bool は `true`/`false`
   - 空文字列でない(空は何にでも「一致」するため、突き合わせ不能として扱う)
   - 正規化値が、**宣言時に蔵(objects/)へ写された成果物**のいずれかに
     部分文字列として現れる

突き合わせ先は宣言時の写し(sha256 固定)であり、**作業ツリーは見ない**。
宣言後に成果物を書き替えても改めには映らない。写しが消えている・ハッシュが合わない場合も
fail である(証拠の消失は機械で捕まえる)。

予行(`monban check`)は 1〜2 のみ(attrs_match は宣言の成果物が要るため、改めで行う)。

## なぜ「同名の全 span 一致」か

蔵は追記専用である。都合の良い数字に「訂正」したトレースを再送しても、元の記録は消えず
二本目として並ぶ。全 span 一致の規則では、成果物がどちらの数字を書いていても
他方の span が矛盾して fail — **差し替え工作は、自分の通り道を自分で塞ぐ**。
人間の上書き裁可(執行規則4)は契約の外の権限として残る。

## 何を証明し、何を証明しないか

- **証明する**: 成果物の数字が、実行中に境界(コレクタ)を通って証言されたこと。
  走らせていないのに数字を書く「過程の作文」はここで止まる。
- **証明しない**: 仕事が正しかったこと。span も成果物も同じ嘘で揃えた捏造は
  otel 検分を通る — それを捕まえるのは再計算(`kind = "toolchain"`)である。
  関は evidence を AND で束ねられるので、**「やったか」は otel、「動くか」は toolchain** を
  同じ関に並べるのが正しい使い方。
- **配備の前提**: 蔵が「エージェントは書けても読めない」であることは、コレクタと OS の
  権限設計の仕事(例: 蔵を別ユーザー所有にし、受口に認証を置く)。門は蔵を読むだけで、
  この性質を作ることはできない。

## semconv との関係

契約は span 名と属性名を**名指し**する。執行機は OTel semantic conventions に依存しない —
標準属性(`gen_ai.*` 等)が改名されても、権威は契約に刻んだ名前である。
計装側が変われば契約を書き替える(契約の差し替えは執行規則2で必ず台帳に写る)。

## 限界(v0 で知っておくこと)

部分文字列一致は素朴である。`"1"` のような短い値は成果物の無関係な箇所に偶然現れ得る。
`attrs_match` には**判別力のある値**(件数・合計・パス・ハッシュ)を選ぶこと。
構造化された突き合わせ(JSON パス等)は、必要が実証されてからの版で検討する。
